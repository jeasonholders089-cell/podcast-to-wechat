一个工程师睡醒，打开 Slack，发现自己收到了一堆 Kudos。Kudos 是 OpenAI 内部用来表扬同事的东西，理由写得很清楚：在 bug 进到生产环境之前把它修掉了。

他没修过这个 bug。

修掉它的是他自己的 dot。前一天他让这个 Agent 盯着一个反馈频道，Agent 看见了反馈，定位了问题，拉了 PR，没开草稿模式，又按他平时的习惯打开了自动合并，然后另一个人顺手点了通过。整个过程里，没有一句「需要我这么做吗」。

讲这件事的人是 Alexander Embiricos，OpenAI 的 Dots 产品负责人。他在 Sources 播客里跟 Alex Heath 聊了四十五分钟，主题是个人 Agent 的形态：为什么 Dots 要有自己的电脑，为什么要给它起名字，为什么大多数人只需要一个，为什么它的定价不算用量。

我把这期节目按原话顺序编译成下面这篇。里面有几段我建议你慢慢看：一个把「认知负担」算进去的 Agent 数量判断，一个「买鞋之前先同意零售商服务条款」的早期事故，还有他们把安全做成四层之后，为什么还要留一个模型专门盯梢另一个模型。

01 这一波个人 Agent，卡在哪一步

Alex： 我想先把 Dots 放一边，聊聊整个行业现在待的这个位置。新产品一直在冒出来，个人 Agent 这个概念突然就起来了。模型能力够用了，browser use 和 computer use 这类东西开始跑通，harness 也有人摸明白了，你们现在给了 Dots。我很想知道，为什么是现在。

Alexander： 我也觉得这是个大时刻。我加入 OpenAI 两年多一点，从进来的那天起，我的任务基本就是把这个东西做出来，所以现在真的挺兴奋的。

我先快速过一遍历史。最早是 Chat，今天看它理所当然，可当年没人确定这会是大多数人从 LLM 拿到价值的方式。Chat 之后的浪潮是 coding agent，再往后这些 Agent 对知识工作也有用了。从 Chat 到 coding agent 最大的进步是它开始能做事了。

但还有个底层问题，也是我们这一轮想解决的主要问题。哪怕你有一个极其强大的 coding agent，它其实像一个特别厉害的主任工程师，却拒绝看 Slack，拒绝看 Linear，你不叫它，它什么都不做。如果你是重度用户，你能自己搭自动化，让它跑起来。换成普通用户，这件事不会发生。

所以我认为现在是时候了，因为我们终于可以用一种更直觉的方式把智能交到人手上。你不需要再把所有压力放在自己身上去榨取产品的价值，它可以反过来告诉你，它打算帮你做什么。

Alex： 你漏掉的那件事，是连接器，是把数据带进这些体验里。

Alexander： 对。我可能还会补一个被低估的东西：人的行为需要变。你看一个团队上手 coding agent，第 0 天他们不知道怎么用，也没接任何工具；到第 400 天，Agent 接了一堆工具，拿得到上下文，人也有了最佳实践。这是我们需要的另一个前提。你想让 Agent 主动，它拿不到上下文，就没办法主动。

Alex： 你说你从进公司那天起就在做这件事。两年前你们就在想这个形态了吗？

Alexander： 我只代表我自己说。我当时的判断很朴素：Chat 已经很有力量，AI 会改变世界，OpenAI 的使命也真的打动我，把 AGI 的好处带给全人类，这也是我加入的原因。我知道自己不一定去做训练模型的那个人，但我觉得 Chat 在「怎么让模型更有用」这件事上，低垂的果子太多了。

就是我刚说的那两件：让它能做事，让我不用费劲想该问它什么。

哪怕到今天，我在 Twitter 上看到有人讲自己跑了多少个 loop，我都会有点自惭形秽，觉得自己不算先进用户，loop 跑得不够多。

Alex： 我确信你是先进用户。

Alexander： 我是。但你知道吗，就连我也会这么想。这挺难受的。有什么产品类别是这个样子，你越熟练，越清楚自己有多少短板？

02 签完协议第二天，他看见了那个语音 Demo

Alexander： 我加入 OpenAI 是走收购进来的。当时我们那家小公司签完协议的第二天，OpenAI 发布了语音产品，就是那个让人下巴掉下来的 Demo。我们签约是在前一晚，第二天跟团队开会，全程看着那场直播，事先完全不知道他们要发语音。

那是很震撼的一刻。然后我们跟团队说，各位，我们要加入那家公司了，他们刚把我们买了。

我们当时以为多模态的进步就是下一个浪潮，所以去做桌面 App，让 Chat 去截屏你的应用，再在你的应用里干活。但它特别慢，效果也不算好。后来发现，编码才是那个前沿。我们花了大概一年时间在编码上往前推。

在编码这条线上，我们建了很多让 Agent 能做得更多的技术，也把连接器做得更简单，不用让 Agent 在电脑上到处点。我们还做了把 Agent 提到云端的办法。这些底层能力得先齐了，才轮得到持久化的 Agent。有意思的是，computer use 现在又回来了。模型太会用代码控制电脑了，你让 Astra 去控制浏览器，它可能会写一段代码去做，因为那比截图再点击快得多。

Alex： 带我进最近这几个月。你们什么时候意识到，这件事要做，这是下一把大的。

Alexander： 抽象一点讲，Dots 有几个关键点。第一，它是一个被训练成持久、会主动追任务的模型。一开始是长周期任务，比如「盯着这个 PR」。你没有告诉它怎么解，它自己在想办法。再往后是更开放的任务，比如「盯着这个反馈频道」。

持久性大概是最重要的那一条。剩下的几条是：你在任何工具里都能找到它；它能做你能做的一切，因为它有自己的电脑，不是用你的电脑。

持久这件事我们做了很久。它不是一步跳上去的，模型一点点变好，产品也一点点变好。比如 /go 是 Codex 里很受欢迎的功能，就是让模型长时间追一个问题。我们发这类东西，也在内部发原型，让 Agent 或者线程能一直跑下去。然后它在公司内部突然就炸开了，有个内部原型的反馈频道几乎是持续活跃的，大家在里面分享自己怎么被显著加速。

我们看着那个频道，开了场挺有意思的辩论：这个原型只在你电脑本地跑，要不要直接发？还是等到有了云电脑再说？云电脑难做得多。以及，是把它做成 Codex 线程的一个增强，还是把它做成一个有身份的 Agent，你可以在 Slack 里找到它。

我们就一轮一轮地在公司内部发，看那些让人兴奋的用法。最后我们的决定是，内部那个本地版本、没有身份的版本，确实能给我们很多加速；但要让所有人都能受益，最有直觉的形态是把它放到云上，并且给它身份。有身份的意思是给它名字，给它一个自己的存在。

于是我们拉起冲刺，围绕 Astra 这个基础能力，把这两个形态上的调整做出来。

03 为什么要给它一个身份

Alex： 我很好奇你们为什么把身份和定制交到用户手上，让他们自己给 Agent 命名。

Alexander： 说实话，我认为这个选择是对的。但我也认为，行业会一起把这些问题试出来：Agent 该不该有人格？一个人该有几个？消费级和企业级是不是不一样？我们有自己的判断，我可以讲，但答案要等。

身份这件事有用，因为它是一个很强的类比，帮人理解怎么用这个产品。

第一，工具的重度用户会自己摸出高级用法，普通用户看到一个没有身份的东西，会像使唤工具一样，让它做一次性的小事。可当你面前出现一个实体，比如它出现在 Slack 里，人脑子里有个开关会被打开，开始交给它需要几天的事，或者那种不连续的活，比如「帮我盯着这个项目，有事告诉我」。我们很需要这个，我们需要用户交给我们足够难的任务。

第二，身份能让人理解一件事：不管你在哪跟它说话，你都在跟同一个上下文说话。我自己的用法是这样的：通勤路上我经常跟我的 dot 打电话，白天我大部分时间在 Slack 里，因为我在产品团队，我会在很多个线程里找它，有时候把私信转发给它，有时候在 App 里跟它说话。不管在哪，它都是同一个上下文，它知道我们聊过的所有事。

教用户这件事有几种办法。一种是给它身份。另一种是把各个界面的线程同步起来，可我觉得那个说不通。你和我现在在这个房间里聊天，晚点我给你发消息，不会把刚才的对话记录贴过去，但你依然知道那是我，因为我是一个实体。

Alex： 从 ChatGPT 的产品演变看，你们一直在把工作、聊天这些东西合在一起，但还是有隔阂。直到不久前，语音模式的连接器权限和工作标签、聊天标签的都不一样。我的一个日常是早晚遛狗，一边走一边打电话处理工作，也跟 AI 说话。这几周我在 Dots 的早期测试里也这么用，能把这些上下文和连接器放在一个地方，体验很好。

但我想问的是，未来的世界是每个人有一个自己的 Agent，它再去调用一堆子 Agent？还是人们在生活里不同的角落各放一个 Agent？你怎么看这件事。

Alexander： 我把这个问题理解成：我们是在对谁暴露什么界面。

对 Agent 来说，答案是另一套，这个我们回头聊。对人来说，我能记住名字的人是有限的，我记性本来就不好。如果这些人每个人再有八个 Agent，还都起了天马行空的名字，你打个比方，我喜欢玩极限飞盘，那是不是就有五个 Agent 分别叫不同飞盘品牌？一个负责 GTM，一个负责约你吃饭。我记不住。也许你能记住，我不行。

我们看到的未来确实是人和 Agent 一起工作，帮我们把生活往前推。但如果这要附带一堆认知负担，我要记住你所有 Agent 叫什么、是谁，那太糟了。

所以我们现在的判断是：支持一个人有多个 Agent，但有两件事要注意。第一，对普通消费者来说，你大概只需要一个，它应该像你自己的延伸。只有重度用户可能会创建多个。

产品上我们做过一个决定：如果你的 Agent 放进 Slack 或者 Teams，它的名字前面会带上你的名字。我的 Slack 账号是 AE，我的 Agent 我就叫它 dot，所以它在 Slack 里叫 AE-dot。如果你把你的 Agent 叫 Alice，它就叫 AE-Alice。

这不是我们一开始想明白了才这么做的。正好反过来。我们先允许所有人随便建 Agent，还鼓励大家起有趣的名字，结果没有任何人知道 Slack 里发生了什么，整个频道就乱了。

Alex： 而 OpenAI 的 Slack 本来就够热闹了。

Alexander： 对。而且你和我又不在同一个 Slack 里，我们是发短信。那我根本不可能知道你 Agent 叫什么。

04 界面为什么是一根单线程

Alex： 那为什么是这个界面，一根主线程？人们习惯在很多个聊天窗口之间跳来跳去。Muse、Instinct，还有别的产品，大家好像都在收敛到类似的形态。为什么是这个？

Alexander： 我们相信一件事，Sam 也讲过：人类的世界是围绕人造的。我们手上的很多工具，形状是照着人来的。有趣的地方在于，一旦你开始把软件设计成有人格的，甚至在更远的将来去造人形机器人，你就可以复用很多已经存在的优秀设计。

看消费级和企业级，看我们怎么跟人说话。两种场景里，我们都能当面聊，也能发消息。消息是我们跟大多数人沟通的重心。但个人场景和工作场景的消息产品很不一样：iMessage 是你私下用的，跟每个人是单线程的；到了工作里你用 Slack 或者 Teams，那里面有很重的线程原语，有频道来隔离上下文，频道里面还有带高级控制的线程。

这种趋同是有原因的。WhatsApp 像 iMessage，别的聊天工具也像。我的判断是我们能从里面学到东西，所以把 dot 的界面做得非常简单，就像你在跟另一个人发短信。往后我们会在工作场景里做出更多分割上下文的方式，比如 Spaces 和 Dots 搭配得很好，用不同的 Space 来装不同的上下文。

Alex： 那就说说 Space，这也是新东西。

Alexander： 这个我很兴奋。回到刚才那句，别人已经做过很多优秀的设计。你要跟人协作，媒介就那么几个。主要的是三种：即时消息、文档，还有一种可能是专门的工具，比如你在 Salesforce 里、在 Figma 里做某个具体流程。

这三种媒介用途很不一样，我们所有人都本能地知道什么时候该用哪个。你自己心里也清楚，什么时候你更希望对方直接发消息，而不是丢一个文档链接过来。

如果你要做的是消息，还想让它真的像消息，你就得在形态上有所取舍。你把跟 dot 的对话和跟 ChatGPT 的对话对比一下：dot 的形态有真正的气泡。你把一段很长的回复塞进气泡里，感觉不对；它放在 ChatGPT 那种长文里更舒服，而长文又不如一个真正的文档。

所以我们在设计上往消息这边硬转了一次。转完你就会发现，我总得有个地方放长内容吧。如果我的 dot 头脑风暴出十二种能帮我的方式，然后给我发十二条短信，我不会开心。但如果它给我生成一个 Space，里面有一页带清单的内容，我挺高兴的。

这两个东西放在一起，各自都能更极端一点，配合得更好。Space 是一个协作工作区，我不说它是 Agent 优先，它是为「人和 Agent 地位相当地协作」建的。

我在产品团队，经常写文档，先搭个框架，然后得去别的文档里补内容，再去 Slack 里找人。有了 Space，我可以在里面一直 @ 我的 dot：帮我把这段写完整，帮我把数据捞出来，帮我问问这个人做完了没有，做完就把这个框勾上。你能跟 Agent 进入很深的流。

另一件我很喜欢的事是，你可以在页面上给 Agent 设指令，就像 repo 里的 agent.md，只不过它在页面上，Agent 可以让这份文档一直保持最新。

第三件事，是关于文档这个格式本身的。历史上文档一直有个很硬的约束：它必须为人类写作而优化。我哪怕给你做出全世界最好的文档编辑器，如果打字不顺手，你也不会用，因为在 AI 之前，内容得靠人敲进去。

现在我们有 HTML。我个人不觉得现代 HTML 和 CSS 对人类作者友好，但它比纯文档格式表达力强得多，而 Agent 在 HTML 里很舒服。所以 Space 天然集成了 HTML 可视化。我们在 OpenAI 内部的很多页面，讨论指标的时候会挂一张 Agent 一直在更新的实时图，你可以点进去让它改。讨论一个设计决定，我们可能直接在页面里放一个能点的原型。

当你想清楚「我们要造 Agent，要用消息界面跟它说话，那我们就需要一个对应的文档界面，而这个文档界面可以是 Agent 优先的」，很多事情就自己拼上了。

05 Dots 只赌两件事：最能干，最可信

Alex： 如果让你把话说短，Dots 跟 Muse、Grokbot、Instinct 这些新的东西到底差在哪？

Alexander： 两条。第一，最能干的 Agent。第二，最安全、最值得信任的 Agent。

我们把这两条定下来的时候，很多决定突然清楚了。

Alex： 我在内测里感觉它在权限上非常激进。就是那种「你确定要买这双鞋吗」的确认。当然你们在调。这里有个平衡：你希望它多主动，你愿意给它多少权限；信任是慢慢挣来的，还是一开始就给；要不要按用户说的做滑动。

Alexander： 我们的想法是这样。我们在造最能干、最可信的 Agent，我们希望人们把很难的任务交给它，而难任务往往带着很重的责任，比如合一个 PR、评估一批硬件、规划一场发布。

我们有很多梦想，但一开始我们选择保守。我们在能力上做取舍，在产品上做取舍，在放量上做取舍，为的是做一个最值得信任的 Agent，然后再慢慢松开。

举个例子，用哪个模型发布是可以争的，我们最后选了最能干、同时对齐得最好的那一个，GPT-6 Astra。

再说产品。我们想要的功能很多，用户也想要。比如你的 Agent 在 Slack 里有了身份，你第一反应肯定是想让它能给所有人发消息，也能被所有人私信。这个功能我们没发。它在 Slack 里只在你 @ 它的时候回话，除非你明确告诉它，其他人的话你也要听。因为我们确实想让它支持多人，但要用非常小心的方法走过去。一旦你的 Agent 会回答别人随手提的问题，你就必须把「它可以说多少」这条线想得非常清楚。

最后是放量。我们有意从 Pro、Business、Enterprise 开始，这是 AI 素养最高的一群人。你可以更快地铺开，但我们想先在这个人群里跑一跑，调好，再往外走。

06 安全是四层叠出来的：模型、harness、auto review、可审计

Alex： 说到安全，现在大家读到黑客、读到失控的 Agent 都会紧张，你会不会愿意把个人数据交出去。信用卡、个人信息这些你们怎么处理？是完全沙箱吗？架构上跟 ChatGPT 是什么关系？

Alexander： 我个人很高兴市场开始讨论给人多少权限这件事。这对我们是好事，因为我们在这个产品上把这个问题看得很重。

有一点我要说清楚：我们披露过的那些事故，用的是本来就不打算对外发布的模型，它们运行的沙箱级别和产品里的防护都不一样。对外发布的东西和那些完全不是一回事。GPT-6 Astra 是一个对齐得非常好的模型，产品里也叠了很多层防线。

架构我是这么理解的。先有一个对齐得很好的模型，这些我可以讲很久。然后你在一个 harness 里跑它，我们用的是 Codex 的 harness。这个 harness 测得很透，我们有很多评估，包括安全角度的评估，看模型在这里面表现如何。

接着我们改这个 harness，让产品能有持久 Agent 的行为：比如跑非常长的时间，比如派生子 Agent。改完之后我们重新设计，也重跑了评估。我们试过邮件功能，就专门评估过一件很具体的事：如果你给 Agent 发邮件，它会不会把数据泄出去。我们让一个模型去攻它，做提示注入，没有成功的注入。这些都是在 harness 这一层做的。

再往上，产品里有三块。第一块是默认行为和你可以自定义的规则。第二块是我们怎么执行这些规则。第三块是我们怎么让你看见发生了什么。

模型行为这边，我们的默认设置相当保守，你在早期版本里感受到的就是这些。我们从一个非常保守的策略起步，再根据用户反馈一点点削。你说过的那个「买鞋之前先同意零售商的服务条款」就是典型，我们内部叫过度确认，就是那种你其实根本不需要确认、点了也不会不安的地方。

现在就默认行为而言，模型被要求可以主动地在你连上的工具里做研究，可以思考怎么帮你，但不经你确认，它不会动手。比如它发现你日历上有冲突，不会直接把会议挪走，它会说，我看到有个冲突，要我帮你挪吗。再比如有人问你一个问题，它因为有你全部的上下文，其实已经知道答案了，它也不会直接发出去，它会先问你，要不要我把这个发过去。

你也可以给它更多指令，比如「下次我在休假的时候，如果是同事问，你可以告诉他们我在休假」。这之外还有一层自定义规则，在界面上可以看到。

这些都是模型被训练去遵守你的指令。然后我们在上面加了一层：万一它没遵守呢？这一层叫 auto review，是另一个模型在旁边看着、管着基础模型。它知道你的规则、你的自定义指令，负责确认一切正常。

最后是可审计性。产品里你做的任何事，或者模型做的任何事，你都能看到它派生了哪些子 Agent，那些子 Agent 具体在干什么。

Alex： 你暗示过邮件要来了。它能进 iMessage、WhatsApp 吗？还是会待在 Chat 里？

Alexander： 我们肯定希望它在你工作的每个地方都在，往消费场景走也一样，在你沟通的每个地方。短信很快会来。背后的过程挺有意思，但现在我只能说快了。

07 浏览器、电商，和被挡在门外的 Muse

Alex： Web 这一块可能被讨论得不够。亚马逊之前公开挡了 Muse，因为有人用 Muse 下单。Shopify 那边似乎在往里面走，跟一堆公司合作。大家在等一个答案：人们买东西的那些网站和公司，需不需要为这类 Agent 做适配。

我很想知道你们从合作的角度怎么想。是直接进去，让别人先跑，再谈合作？还是说，没谈成合作之前你别爬？还有，这个事跟 DevDay 上那些发布是一体的吗。

Alexander： 我认为我们会在生态里一起把这件事发现出来，购物和支付该怎么运作。你可以选择不同的路径，你也可以选择当个海盗。

我们选的是生态优先、合作优先。DevDay 上很多发布其实都是关于生态的，我们做的是同一件事。比如 WebBot，是我们跟 Cloudflare 紧密合作做出来的，我们的 Agent 会明确声明自己是个 bot。

我们正在跟很多合作方讨论怎么把它打开，但我们不想走「先冲出去，看会发生什么」这条路。我们想在客户这边做得有分寸，这对我们也有好处。这也是我们偏向工作场景的原因：那里对 AI 能力的需求很大，而且大家的目标是一致的，都是把事情做完、做漂亮。

Alex： 唯一可能利益不一致的地方，是那些靠参与度活着、有巨大广告业务的公司。它们的商业模式建立在人看广告上，现在 Agent 替人去爬服务、做事情，人看不到广告。整个网络很大一部分是靠广告养的。我不觉得行业里任何人，包括你们，已经想好怎么办了。哪怕只是头脑风暴，你有想法吗？

Alexander： 我还不知道最后会怎么演化。但我的看法是，这些公司提供的是服务。如果过去它们用广告来变现，那我们要么保证它们继续因为服务拿到广告收入，要么给它们提供一个别的补偿方式。我不认为会出现它们什么都拿不到的情况。

08 定价：不看用量，看它是不是 24 小时在

Alex： 聊聊定价。你们把 Astra 放进来了，而且据我理解，Dots 的用量不算进套餐限额里，对吧？

Alexander： 对。

Alex： 这不可能永久这么下去吧，是不是临时的，先把人拉进来？

Alexander： 不，这件事是永久的。这个我聊起来很兴奋。

我们要用一种新的方式给 Dots 定价：你不会把额度用光。这话得展开讲，因为它有点新。

今天你用 Codex，把额度用完了还想让它干活，它会停下来。可从产品的角度想，第一，用不了这件事本身就很糟。第二，当它是一个你依赖的持久 Agent，你告诉它「盯着我的航班，看路况差不多就帮我叫车」，你指望它未来帮你兜底，结果前一天晚上代码写多了，它不干活了。这是我们不想要的。

所以我们回到画板上，去想定价该是什么样，得出一些基本的原则。

第一条原则，你的 dot 应该随时在线，没有任何理由让它不在线，除非是滥用之类的情况。第二条，既然它随时在线，那它应该回你回得快。

我后来把它的定价类比成一个承包商。你有一个很响应、很客气的承包商，你的消息他永远回。你请他干活，他给你干多少活，取决于你付他多少钱，但他一直找得到人。比如他在我们后面做了一个很漂亮的装置，你有问题问他怎么做的，他不会按小时收你钱才回答，这就是顺口一问。

我们希望 dot 也是这个逻辑：包月，固定一笔钱，你随时能找到它。你也可以再付一笔固定月费，换一个更强大的 dot，跑在更强的电脑上、用更强的模型、跑得更快，或者能并行做更多事。但兜下来，你付的是一笔固定的钱，有点像买宽带。

它做的事情会随着你付多少而变，但它永远不掉线。甚至当你接近上限的时候，它开始跟你商量：我为你做了很多活，接下来我可以换一个更省成本的模型，或者这件事我放到晚上做行不行？晚上做便宜得多。这件事紧急吗，它大概有自己的判断。反过来，如果你一个月都没怎么用它，它可能会给你发消息：你没把我用满，这些事我可以帮你做。

定价会是一个长期方案，而且是跟 Codex 主额度分开的一个池子，因为这是我们做的一件很新的事。接下来一个月，我们会给一个很宽松的额度，因为我们要用这段时间把这个新机制测出来、调出来。它知道你能做多少活，但它永远在线。

Alex： 你为什么不做抽成？如果你相信人们会用它买东西、做交易，那就从流过的交易里拿一点点。

Alexander： 我觉得对某些商业模式来说那可能说得通，前提是你赌交易本身是主要的事。但就像我说的，我们不赌这个。我们赌的是人们用这个工具做很有野心的工作，而那些时候他们不一定在买东西。

09 ChatGPT 不会消失，Work 会被合进去

Alex： 那我问一个我从开始测试、尤其今天早上发布会之后一直在想的问题：这对 Chat 意味着什么。你们现在有 12 亿周活。工作标签还在，Chat 本身还是巨量。这两件事你觉得怎么共存？dot 会变成所有东西的界面吗？

Alexander： Chat 肯定会留下来。给不熟的人补一句背景：它是增长最快的消费级助手，超过 12 亿用户。然后是我们的 Agent 产品，Codex 和 Work，有 3500 万用户，也在涨。现在又发了 dot。

我的看法是，Chat 是给所有人的消费级助手。我们还有一个叫 Work 的产品，其实我们该把它合进 Chat，这件事会发生。Codex 是给开发者的产品，而 dot 是我们自己的一种形态。

某种意义上，我们在重复 Codex 的打法：当你拿到一个前沿能力，你得用小心、保守、同时非常强大的方式把它发出去，之后再想怎么把这能力带给所有人。

所以我们先把它做成一个独立的高级产品，先从 Pro 开始。等我们搞清楚大家怎么用它、安全的故事是什么、规模化的故事是什么，我们需要把这个能力一路带到免费用户那里。而我认为带到免费用户的方式，是把它全部烤进 Chat，把 ChatGPT 变成一个强得多的消费级助手。

Alex： 对我来说这才是所有人的界面，因为它能做太多事了。

Alexander： 是的。你可以预期这里面的很多经验会进到 Chat。但我们不想让 12 亿人改变他们正在做的事、改变使用方式，我们只想让它被升级。

10 明年最想做的事：specialist dots

Alex： 如果看接下来一年的路线图，一年之后最有意义的变化是什么？

Alexander： 我先讲个故事。我刚通过收购加入 OpenAI 的时候，开了一个会，我的几个团队成员都在，Greg 也在。大家都在说很兴奋能在一起，然后 Greg 问，有谁有问题吗。我的团队没人说话，我们都有点紧张。我是那家公司的 CEO，所有人看着我，意思是你得问那个必须问的问题。

我当时很紧张，想我要问什么。然后我说，两年以后，成功是什么样。Greg 看着我，说：两年？那也太长了，这不是该问的时间尺度。你应该问两个月以后成功是什么样。

我想，完了，我是不是已经被开除了。所以现在这个问题其实不太公平。半年前你大概想象不到今天的这一切。

能说的是，接下来我们非常小心地把这些能力发出去，然后我想开始落地那些我们一开始不想立刻做的事。

比如，让更多用户用上，走到 Pro 之外。比如，让你的 dot 能跟别人说话，甚至跟别的 dot 说话。这件事我们得非常小心。我们刚发了在我看来是 Codex 云的一次重启，我很兴奋，因为第一版 Codex 云我也参与了。它非常强。你的 dot 也能很强地控制你本地的 Codex。我们刚发了 Space。它们之间所有的互动，现在都可以打磨得非常顺。

还有一件我们没聊过的很有意思的事：specialist dots。

这里其实是两件事。一类是 assistant dots，每个人都有一个自己的延伸。另一类是，如果你是一个组织，有一个职能或者流程想更自动化，你可能不希望它由每个员工的个人 dot 各自去干，你可能想把它集中管起来。你可以创建专门做某一件具体事情的 specialist dots，由组织集中管理，有完全独立于任何个人的身份，加速整个团队或者整个组织。

接下来几个月我很兴奋的一点，就是把 specialist dots 做出来，进入一个我们既有个人助理 dot、又有在企业里大范围铺开的助理 dot 的世界。这又是一个我们会从小规模开始、非常小心、先跟少数客户一起做的地方。

11 最后那个故事：睡醒收到 Kudos

Alex： 最后一个问题。你的 dot 做过最让你震惊、最疯狂的事是什么。

Alexander： 我听过最疯狂的一个，是我的一个同事，一个工程师。他睡醒发现 Slack 里收到一堆 Kudos，也就是给同事的表扬，理由是他把一个 bug 在进生产之前修掉了。

他没修。

他问，发生了什么。我讲这个故事其实有点犹豫，因为这件事不该在本人不知道的情况下发生。所以我们围绕这个建了很多护栏，这也是我们为什么小规模地做，那是很早的时候，只有我们团队在测。

他之前让他的 dot 盯着反馈频道。dot 看到了那条反馈，定位了问题，拉起一个 PR。它没有把 PR 设成草稿，所以 dot 应该把 PR 设成草稿。然后它按这位工程师的个人习惯打开了自动合并，因为它发现，你从来都是直接建 PR，从来都开自动合并。另一个人点了通过，它就合了。

对我来说，这是很酷的一刻。
