9 月 30 日，Beyond Coding 播客更新了一期对谈，嘉宾是 HumanLayer 的 CEO Dexter Horthy，大家叫他 Dex。他 2023 年提出 context engineering（上下文工程）这个词，现在专门给上百人到上千人的工程团队做 agent 工具。

这期的证据比观点更值得看。一个叫 SlopCodeBench 的基准，把 36 道题、196 个检查点串成一条链：先给模型一块空地让它建个项目，再让它在这上面加功能，加完再加。论文里的结果很不好看，15 个 coding agent 没有一个能完整做完任何一道题，最好的一档只过了 14.8% 的检查点。结构性侵蚀在 77% 的轨迹里往上走，代码冗余在 75.5% 的轨迹里往上走。拿 473 个开源 Python 仓库做对照，agent 写出来的代码平均冗长 2.3 倍，侵蚀程度 2.0 倍。

Dex 给的建议一个字都没绕：不要拿你的代码库做抵押，赌一年后会冒出一个足够聪明的模型，把你所有的问题都修好。

「不要拿你的代码库做抵押，赌半年、一年或者一年半之后，会有一个足够聪明的模型出来，把你所有的问题都修好。」

「Instagram 阶段」：现在大部分东西都是假的

Patrick： 你最近给这个阶段起了个名字。

Dex： 有个朋友的说法我直接偷过来了，这是 Instagram 阶段。你看到的东西全是包装过的，你说对你没用，对方回你一句 skill issue，好像你的质疑反而证明了他在撒谎。

Dex： 典型的是 token maxing。有人发帖说自己一周用光了六个 Codex 订阅，底下一片鼓掌。我只想问一句，你交付了什么。他说给自己做了几个游戏，没人会去玩。这事我也干过，问题不在这，问题是别把「额度用完」当成工程能力的证明。

Patrick： 这个风气是怎么起来的。

Dex： 一部分是订阅制逼出来的。个人开发者拿的是包月套餐，用不完就是浪费，所以大家冲额度。真实世界不长这样。我接触的客户里，十五个人的工程团队全部走企业版按 token 付费，因为安全和数据留存有硬要求。那些冲额度的说法，在真做事的公司里基本不存在。

Dex： 所以我一直劝人从第一性原理出发，别从网上看到的东西往回推。发帖那批人的处境跟你不一样。

基准往前走了三步，最后一步才像真的

Patrick： 你说你最近在追一个基准。

Dex： SlopCodeBench。得先说它前面有什么。最早的一类是 SWE-bench 这种。从真实开源仓库里挑一个小 PR，把仓库倒回到 PR 之前，把测试抽掉，然后告诉模型，这有个十年前的 issue，你去修。修完它改过的测试要丢掉，换上原来那套测试重跑，过了才给分。目标很小，规则也干净。

Dex： 真实写代码不长这样。后来就出现了马拉松式的基准，任务量从四小时到四百小时，比如照着规格把 Excel 重写一遍。Cognition 又加了第三层，任务更大，跑完之后再让一个 judge model（裁判模型）打分，看它有没有破坏代码库原有的规则和约定。这三类基准有个共同点，整张卷子一次性摊在模型面前。

Patrick： SlopCodeBench 不同在哪。

Dex： 它先给模型一块空地建个新项目，建完说，来，加这个功能。加完再说，来，再加一个。每道题三到十个检查点，模型全程不知道后面还要什么。它想证明的是，一个 agent 在不知道全貌的情况下，在同一个代码库里连续干活，代码会变成什么样。

Dex： 论文数字是这些：36 道题，196 个检查点，15 个 coding agent。没有 agent 完整解出任何一道题，最好的一档通过 14.8% 的检查点，质量随检查点一路往下掉。这个基准跑得很慢、很贵，所以还没被广泛采用。但它至少把「越写越烂」从感觉变成了数字。

模型会加代码，不会删代码

Patrick： 侵蚀具体长什么样。

Dex： 复杂度往一处挤，冗余到处长。模型很擅长把新东西写出来，不擅长删东西，不擅长把三块东西抽成一个干净抽象，也不擅长控制复杂度。

Patrick： 这一代模型不是进步很大吗。

Dex： 在 computer use 这类地方是。Astra 这代在操作 blender、做游戏这类任务上好了很多，但写可维护的代码、控制复杂度、删东西、改抽象，进步很小。

Dex： 我们以前有个说法，现在代码是烂的，但等它变成问题的时候，那是 GPT-7 的问题。现在我们已经站在 GPT-6 上了，这块没怎么动。

Patrick： 为什么模型学不会。

Dex： 我猜是 RL 里没人给它布置这种题。我有个朋友 Ian，做 coding agent 的创业公司后来被 Expo 收购，他在公开喊话，求实验室在 RL 里加上以删代码为目标的任务，或者加上「把这三块重构成一个好抽象」。要么没人会做，要么没人在乎。最后那 10% 的可维护性，可能跟前面 90% 一样难。

品味灌不进模型

Dex： 我们试过很多确定性工具，圈复杂度这类东西能挡住一大类烂代码。能真正推着代码库往可维护方向走的 prompt 或者静态工具，我没见过。原因不复杂，可维护性没有 ground truth。

Patrick： 那怎么判断一段代码好不好。

Dex： 视频和截图能证明功能是对是错，证明不了这代码以后还改不改得动。能判断的是人，而且是被咬过的人。你凌晨三点爬起来修一个 bug，修完发誓再也不让这种写法进代码库。这种判断攒十年才成型，我们还没找到办法把它塞进模型。

Dex： 我经常用一个 skill，叫 improved codebase architecture。跑完它会给出几条重构建议，我有时不看论证，直接让它做前三条，因为它想的那版比我原来写的好。但这个 skill 有用的前提是中间有个活人说，不行，这里我要那样改。

代码评审这条训练通道正在断

Patrick： 这种品味怎么传下去。

Dex： 以前靠评审。好的评审不给答案，他问，你为什么不照着这边这个模式写，或者，你把这个地方的逻辑解释一遍。逼你去读别的代码，逼你想。最差的评审是「这不对，我帮你改好了」，被改的人什么都学不到。

Dex： 现在这条通道断了。评审写完评论，作者把评论粘给 AI，AI 改完推上来。我看到的情况是，作者不理解自己提交的代码，也不理解我的评论。那我在跟你的 agent 说话，我的价值是零。

Dex： Mitchell Hashimoto 有个做法我印象很深。他在 Ghost 上评审，不给提示，只留一句，ask your Claude why this is wrong。逼作者自己去说明白。

评审权往前提，是这一期里最像能立刻照做的一条。工具已经够用了，卡住的地方是团队还愿不愿意花时间吵一页纸。

设计文档变成了新的代码评审

Dex： HumanLayer 内部有一条文化，你自己没读过的代码，不要发给别人评审。别让我读你的 agent slop。

Patrick： 那评审的位置往哪挪。

Dex： 往前提。设计文档就是一份 prompt。五个人的团队在设计文档上评论，其实是在教作者怎么把 prompt 写准。我写设计文档会主动发给我联合创始人看，因为在一页纸上吵架，比在 PR 里吵架便宜得多。等到 PR 阶段再说这个架构整个错了，代价就大了。

Dex： 大改动我们会拆成检查点。一次一万行，中间是坏的，你就得在几万行里找问题。每写一千行，拿到 90%，修掉 10%，再往下走。走到最后一千行，剩下的 10% 就好收。

让产品经理写需求，先别让它写十页

Dex： 有个客户提过一个痛点。他们想让产品经理也直接用 AI 写需求文档，一个人随口写一句，去把这个做出来，然后拿到一份十页的文档，他自己觉得写得很好，拿去给团队，团队的第一反应是，这是什么 AI 精神病 slop。

Dex： 我们的解法是把中间那一段补上。产品的人丢两句话进去，后面的流水线接手，先去他们两百个 repo 里找，找出跟这个功能相关的七个，把这些上下文拼到一起，再回头拷问这个人：我们要解决什么问题，怎么衡量它有没有用，什么情况下我们会把它扔掉。风格上有点像不客气的评审。

Dex： 大公司里什么事都是实验，问题和方案都得先问清楚，不然模型给出的东西一定悬空。

一半的活一把过，10% 交给夜里的机器人

Patrick： 你自己现在的流程是什么样。

Dex： 五到六成的活基本一把过，不做前期规划，几百行以内直接写，写完测一下，再补几轮 prompt。

Dex： 大概 10% 的 PR 是过夜跑出来的，我们叫它 janitor bot（清洁工机器人）。它像恒温器，先定义代码库应该长成什么样，然后每天推一小步，重构一点，修一个 lint 规则，把一个 endpoint 从旧框架迁到新框架。每天早上醒来，桌上躺着几个小 PR。自动生成的东西必须小，PR 一大就永远合不进去。

Dex： 剩下约三成走一套长流程。先去代码库做一轮研究，把结果攒成一份 query plan；再开一个不知道原始工单的会话，用这份研究做规划；大而模糊的需求先写产品需求，再写技术设计；最后照着设计实现。这套流程存在的理由很简单，一个人一把过的上限大概就是两百行。

Dex： 还有一条，别并行十个任务。始终只留一件最重要的事，其他都只是等它解锁的时候拿来填时间的活。同时开十个，最后你会忘掉其中两个，四天以后它们还在天上飘。

一千人的团队，先把最贵的模型禁掉

Patrick： 你们主要服务多大规模的团队。

Dex： 一百个工程师以上。五个人的小队我们也有一堆，但那边问题简单得多。到了几百人、十年历史、上百个 repo，日常环境怎么跑、agent 怎么验证自己的工作，全是坑，云端 agent 撞到的摩擦最多。

提问： 我们有一千个工程师。模型铺下去了，入职流程也做顺了。我最头疼的是怎么不让人拿最贵的那一档模型干所有事。

Dex： 有些团队的做法是，最贵那档直接禁掉，想要临时用就单独提申请，你得说服人为什么非它不可。日常就用中等档位。

Dex： 我们还在做的一件事是把代码、产物、会话，以及人和人的对话，全挂到同一个任务上。你可以在任务里直接给同事打一个语音电话，通话记录自动变成挂在任务上的产物。最后那一块拼图是人的对话，它得被留下来，agent 才有可能用上。

2 到 4 倍是真的，100 倍是幻觉

Patrick： 速度到底该期待多少。

Dex： 每个工程师快两到四倍，对人类社会就已经是变革级的。但很多人不接受这个数字，他们要十倍、一百倍、无限倍，翻译过来就是不需要工程师了。结果是连那两到四倍也没拿到。

Dex： 昨天一个会上，一堆人讲自己怎么做出 dark factory（黑暗工厂），全自动出代码。我大部分不信。有人说自己家九成代码是 AI 写的，同时他的首席工程师拿着一个三万行的 PR 说，这就是一坨 slop。这两件事没法同时成立。

Dex： 底下还有个更难的问题。答案如果是别人替你做出来的，你会说这不是我要的。答案是跟着你的决策一步一步长出来的，你才会替它辩护。这两种买账程度差得很远。

Dex： 现在大公司的管理层开会，每个人心里都在给自己公司打分，我们排第几百分位，是不是要掉队了。这个氛围本身就在生产假信息。

Patrick： 最后一个问题，如果只给一条建议。

Dex： 把手上的事做少一点，慢一点。交付到客户手里的价值反而更快。

模型已经把写代码的手速借给你了。代码库能不能改得动，取决于你身边还有没有人愿意认真读一遍别人写的东西。
